# Tickdroid — Architecture & Implementation Plan

Companion Android app to the Tickbuddy Nextcloud webapp. See `README.md` for product context and `mobile_instructions.md` for the authoritative API / sync handoff doc (the code wins if it disagrees).

This file captures the current state of the codebase and decisions made along the way. Update it as decisions change.

## Scope decisions (v1)

- **Auth**: pasted Nextcloud app password. Login Flow v2 stubbed but not implemented — seam exists in `AuthRepository.beginLoginFlowV2()`.
- **HTTPS only**: the early "Allow http://" toggle was removed. `ServerUrl.normalize` rejects anything but `https://`.
- **TLS trust**: `res/xml/network_security_config.xml` trusts `system` **and** `user` CA stores, so self-hosted servers behind a private/self-signed CA work once the user installs that CA on the device (issue #37). Chain, hostname and expiry are still fully verified — there is deliberately no "ignore TLS errors" switch, and adding one would be a regression (it is what Google's [policy page](https://support.google.com/faqs/answer/6346016) warns against, and the likely route to an F-Droid anti-feature). Two traps: the config **cannot** be narrowed with `<domain-config>` because the server hostname is entered at runtime and the file is a static resource; and `app/src/debug/res/xml/` **overrides** it in debug builds, so the debug copy must stay a superset of the main one or the feature silently vanishes from every build a developer tests on. Per-certificate trust-on-first-use (the model the Nextcloud Android client uses) is the stronger design and remains unbuilt — see "Future considerations".
- **TLS failures are classified, not lumped in with "unreachable"**: `SSLHandshakeException` / `SSLPeerUnverifiedException` are `IOException` subtypes, so without care they land in the generic "could not reach the server, check the URL and your network" branch — advice that points at three things that are all fine. `AuthProber` catches `SSLException` **before** `IOException` at all three probe stages (Kotlin matches catch clauses in order — the ordering is the whole mechanism) and returns `AuthProbeResult.UntrustedCertificate`; `SyncManager.pull` and `PushWorker` do the same for `SyncErrorKind.UntrustedCertificate`. Catch `SSLException`, **not** `CertificateException` — the latter is never the thrown type, only a cause several links down. And classify on exception *type*, never on `message` text: the wording comes from the platform TLS provider (Conscrypt on device, SunJSSE under JVM unit tests) and differs between them, so unmatched detail is passed through verbatim rather than guessed at. Coverage: `AuthProberTlsTest` (real TLS socket, cert from a CA the client doesn't know).
- **History depth**: full database, infinite scroll backwards in 30-day windows from day 1.
- **Private tracks**: simple show/hide toggle (App settings → Show private tracks). No PIN/biometric gate.
- **Counter UX**: short tap +1, long tap −1 (no-op when value is already 0).
- **Counter conflicts**: on a Tickbuddy with `counterIncrement` + `idempotencyKey` (2.3.0), a counter day goes up as the change made on this phone (`increment`), so other devices' and scripts' changes are kept (see "Push"). On an older server it is still silent last-write-wins: an absolute `set`, so two devices both incrementing on the same day lose one increment. Not surfaced in UI.
- **Sign-out**: calls `database.clearAllTables()`, resets `UiPreferences` (`clear()`) and clears `WidgetConfigStore` so the next user on the same device doesn't inherit cached data, queued writes, UI settings (theme, density, journal layout, editable-days, show-private), or widget setups. **Never `close()` the database here.** `TickdroidDatabase` is a Hilt `@Singleton`; nothing recreates it, so closing leaves every consumer (SyncManager, the repositories, the injected DAOs) holding a dead instance for the rest of the process, and signing back in without killing the app crashes on the first query with `SQLException: connection is closed`. An earlier version closed and deleted the DB *file* to avoid `clearAllTables()` running migrations on a stale on-disk schema; that trade was wrong — there is no destructive-migration fallback, so a stale schema crashes at startup long before anyone reaches sign-out. The wipe is gated on a real `SignedIn → SignedOut` transition (`SyncCoordinator` tracks the previous state) and runs under `SyncManager.runExclusive` so it can't race an in-flight pull. Regression coverage: `SyncCoordinatorTest.signOut_thenSignInAgain_leavesDatabaseUsable`.
- **Editability**: configurable in App settings. Choices: today only / today + previous day / last 7 days / all past days. Future days never editable. Tapping a locked cell shows a Toast.
- **Track management is online only**: add, rename, make private/public, reorder and delete are direct server calls made under the sync lock and followed by a re-read of the track list in the same hold (`SyncManager.changeTracks`, see "Sync layer"). There is no offline queue; offline, those controls are greyed out and a tap explains why. Colour and icon stay local (`track_prefs`) and editable offline. Changing a track's type is not offered (the server ignores it).
- **Archive / restore** (roadmap step 5b, needs a Tickbuddy with the `archivedTracks` capability flag; without it the app behaves exactly like 1.2.0 apart from the help sheet's offline sentence). Archive from the track screen ("Archive track" + confirm) or the delete confirm ("Archive instead", no second confirm); restore or delete from the collapsed "Archived (n)" row at the bottom of Tracks settings. Online only, like every track change. Archived tracks stay in Room (with their ticks, colour and icon) but never reach the journal, the widgets or widget setup. The archive date is the phone's own `clock.today()`.
- **Unknown track types are read-only, never a crash** (groundwork for Number / Choice, brief of 21 Oct 2026). `TrackType` is a sealed interface — `YesNo`, `Counter`, `Unknown(wireValue)` — and `fromWire` never throws (it used to, from `TrackEntity.toDomain()`, which would have crashed every screen and widget redraw). Such a track shows everywhere — journal, Tracks settings, track screen, all three widgets and widget setup — with "Tickdroid update required" in place of its type label; its cells draw the ticked colour with "?" when the value is above 0 and the plain empty cell otherwise (no "·" / "+" hint); a tap (editable or locked day, journal or widget) only toasts "*Name*: Tickdroid update required." and its content description is "*Name*, Tickdroid update required". Track management (rename, Private, colour, icon, reorder, archive, restore, delete) is untouched. Widget taps use `ReadOnlyTapAction` (carries `KeyTrackName`, writes nothing, so no stale-day check); `WidgetTickHandler.onTap` also returns `Ignored` for one as a guard. The shared strings are in `ui/common/UpdateRequired.kt`. `NewTrackSheet` still only offers Yes/No and Counter (it saves the type's wire value in `rememberSaveable`: a sealed type isn't Bundle-able). **For the release that first learns a new type** (agreed 21 Oct): it must delete the local ticks of every track whose type it newly understands on first start (they hold this release's 1/0 markers, see "Network"), and keep such a track locked until its first successful sync after the update, or an offline install could overwrite the server's value. Room already keeps the raw type string, so nothing more is needed now.
- **Today and the bottom bar** (spec "the Today screen and notes", decisions of 28 Oct 2026). Two main screens, **Today** and **Journal**, each with a Material 3 `NavigationBar` (web icons: `CheckBox`, `CalendarMonth`, filled when selected). Today opens **only on a start from nothing** (swiped from recents, reboot, update, any sign-in); coming back to the app, by recents, launcher or widget, always returns to the screen that was left (the platform's own saved state; nothing is stored for it). Tapping Today in the bar shows today; Back on the Journal goes to Today, Back on Today leaves the app, except right after a Journal day label opened it (then Back returns to the Journal, until a bar item is tapped).
- **Notes** (Tickbuddy flags `notes` / `notesAppend`): one plain-text note per track per day, at most 500 code points, read and written on Today in a card docked over the keyboard, marked with a dot in the Journal. Written to Room straight away and pushed later; a note changed elsewhere meanwhile is **merged with `append`** (only the phone's new lines go up, nothing on the server is removed), or overwritten by the phone's version on a server without `notesAppend`. Without `notes` there is no note UI anywhere and no notes request. Notes on a track of an unknown type can be read and written (only its cell is read-only).
- **Streaks come from the server** (`GET /api/stats?today=…`, flag `stats`), read at every pull and kept in Room (`track_runs`), so they show offline but only update after a sync (a second or two after a tick online). No phone-side streak rule. Without `stats`, no streak text.
- **Out of scope for v1** (deferred): Login Flow v2, import/export, daily reminder, real schema migrations.

## Release build

- `isMinifyEnabled = true` for the `release` build type — R8 strips/shrinks/optimizes. `proguard-rules.pro` has three custom rules (the third is below): `-dontwarn com.google.errorprone.annotations.**` (Tink ships errorprone annotation references that aren't on the runtime classpath; benign compile-time-only suppression), and `-keep class * implements androidx.glance.appwidget.action.ActionCallback { <init>(); }`. **Do not drop the second one.** Glance creates widget tap callbacks by reflection (`getDeclaredConstructor().newInstance()`); its own consumer rule keeps the classes but, under R8 full mode, not their no-arg constructors, so without it every widget tap silently fails in release builds only (debug is unminified, and the tests run debug). Verified by `dexdump` on the release APK. A third rule, `-keep class * extends androidx.glance.appwidget.GlanceAppWidget`, stops R8 **merging the three widget classes into one**: Glance finds a widget's ids by the GlanceAppWidget's class name, so after the merge every kind's `updateAll` also drew its own UI into the other kinds' widgets (on a real phone, a list widget showing the Single track's "Choose track"). `updateAllWidgets` also no longer uses Glance's `updateAll`; it takes each kind's ids from its manifest receiver, so neither class names nor Glance's on-disk name cache can cross kinds. **Release check:** after `assembleRelease`, `grep -E '^com\.martinhammer\.tickdroid\.widget\.(SingleTrackWidget|TodayListWidget|TodayRowWidget) ' app/build/outputs/mapping/release/mapping.txt` must list all three, each mapped to its own name. Both bugs are invisible in debug builds and in every test, which all run unminified. All other libraries (Retrofit, kotlinx-serialization, Room, Hilt, OkHttp, the rest of Glance) ship sufficient consumer rules.
- `android:allowBackup="false"` in the manifest. Auto Backup and device-to-device transfer are both disabled to keep `EncryptedSharedPreferences` credentials (key bound to the device Keystore) from ending up in a backup that can't be restored. Local state is recoverable by re-syncing from Nextcloud; only per-track color/emoji overrides (`track_prefs`) would be lost on reinstall.
- F-Droid builds from source and — because reproducible builds are enabled (see below) — ships the APK signed with **our** key rather than theirs. Local release APKs need to be signed (e.g. with the debug keystore via `apksigner`) only for sideload testing.

## F-Droid publishing

Submitted for inclusion on 2026-07-23 via merge request [fdroiddata!43688](https://gitlab.com/fdroid/fdroiddata/-/merge_requests/43688), which closes [rfp#3903](https://gitlab.com/fdroid/rfp/-/issues/3903). The recipe lives in F-Droid's own `fdroiddata` repo at `metadata/com.martinhammer.tickdroid.yml`, **not** in this repo. Because it sets `AutoUpdateMode: Version` + `UpdateCheckMode: Tags`, F-Droid picks up new `v*` tags automatically — the recipe shouldn't need further edits for routine releases.

**Reproducible builds are enabled** (`Binaries` + `AllowedAPKSigningKeys` in the recipe), so the F-Droid build is verified byte-identical to our published APK and then signed with our certificate (SHA-256 `a398f829a84c52c9a8bbf2c1357f036b8e822b71ca86f56edebe36bda8ba1c3c`). That keeps one signature across GitHub, F-Droid, and — if it's ever added — Play, so users can move between sources without uninstalling. It is also effectively a one-way door: had we let F-Droid sign with their key, switching later would break updates for existing users.

Two constraints follow, and both are easy to trip over months from now:

- **Never re-enable `dependenciesInfo.includeInApk`.** AGP embeds a Google-key-encrypted dependency-metadata blob in the APK signing block by default. F-Droid's `check apk` scanner rejects it outright (`ERROR Found extra signing block 'Dependency metadata'`) and it is non-reproducible anyway. `includeInBundle = true` is deliberately kept so Play would still get dependency insights — the two flags apply to different artifacts (`assembleRelease` vs `bundleRelease`) and never interact.
- **Every release must stay byte-reproducible and be published at the `Binaries` URL**, i.e. a `tickdroid-<versionName>.apk` asset attached to the `v<versionName>` GitHub release. F-Droid rebuilds from the tag and compares against exactly that file; if it diverges, the release can't ship with our signature. Also keep signing with the same keystore — a different cert breaks `AllowedAPKSigningKeys`.

To sanity-check a release APK before publishing, enumerate its APK Signing Block IDs: expect only `0x7109871a` (v2 signature) and `0x42726577` (verity padding), and **never** `0x504b4453` (dependency metadata). Verifying content reproducibility is a `unzip -v` CRC comparison against F-Droid's from-source build — v2-only signing adds no zip entries, so every entry's CRC must match.

## Data layer

**Room schema (v5)**:

- `tracks(localId PK, serverId?, name, type, sortOrder, private, archivedAt?, dirty, deleted, updatedAtLocal)` — `archivedAt` is a nullable ISO `YYYY-MM-DD` (null = active), added by `MIGRATION_2_3` (`data/local/Migrations.kt`, one `ALTER TABLE … ADD COLUMN archivedAt TEXT`, no default so it matches the entity; covered by `MigrationTest`, which reads `app/schemas/` as androidTest assets). `dirty/deleted/updatedAtLocal` are still inert (track management is online only); dropping them needs a full rebuild of `tracks`, the parent of the `ticks` foreign key, so it is its own later migration, not folded into v3.
- `ticks(localId PK, serverId?, trackLocalId FK, date TEXT, value INT, dirty, deleted, updatedAtLocal, pendingDelta?, sentDelta?, sentKey?)` — unique index on `(trackLocalId, date)`. The last three were added by `MIGRATION_3_4` (three `ADD COLUMN`s, no defaults, so every existing row reads null; `MigrationTest.migrate3To4_…`) and are only ever set on counter rows (yes/no rows hold null). `pendingDelta`: **null on a clean row**; on a **dirty row, a number** (possibly 0) is the net change made on this phone since the last value the server confirmed (so `value` = that value + `pendingDelta`), and **null** means `value` is absolute and goes up with `set` — a change queued by v3 or older, whose delta can't be worked out (pushed once more that way; the day uses `increment` after). `sentDelta` + `sentKey` (both set or both null): an increment sent, or about to be, whose answer hasn't arrived — its exact delta and its `Idempotency-Key`; `pendingDelta` includes `sentDelta`, so taps made since are `pendingDelta − sentDelta`. They live in Room because the uncertain case (answer lost, worker stopped, app killed) is exactly when the process may go.
- `track_prefs(serverId PK, colorKey?, emoji?)` — local-only UI overrides keyed by `serverId`. Never synced.
- `notes(localId PK, trackLocalId FK, date TEXT, text, dirty, baseText?)` — unique on `(trackLocalId, date)`, `ON DELETE CASCADE` from `tracks`; no `serverId` (the server has no note ids). Added with `track_runs` by `MIGRATION_4_5` (SQL copied from `5.json`'s `createSql`; `MigrationTest.migrate4To5_…`). `text` is what the phone shows, normalised (`normaliseNote`, the server's own trim). Clean rows hold the server's note; only a **dirty** row may hold `""` (the phone deleted the note). `baseText` is set only on dirty rows: the server's note as the phone last knew it **when the change began** (`""` for none), kept through every later edit until the push settles the row — it is what lets the push tell the phone's new lines from another writer's. `NoteDao.observeRange` leaves out `""` rows; `getRange` (the pull's) includes them, as `TickDao.getRange` does deleted ticks.
- `track_runs(trackLocalId PK + FK, asOf, isStreak?, length?, upToYesterday, maxValue)` — the stats answer as of `asOf` (the phone's today), replaced wholesale on every read (`TrackRunDao.replaceAll`). `isStreak`/`length` null = no ticks. `maxValue` drives the Today squares' shading.

**Network**:

- `OcsEnvelope<T>` with a Retrofit-friendly shape that exposes `.ocs.data`.
- `OcsHeadersInterceptor` adds `OCS-APIRequest: true` and `Accept: application/json`, plus `Prefer: handling=strict` (RFC 7240) on Tickbuddy's API paths only, so a current Tickbuddy answers a write to an archived track with **423** instead of a quiet 200 (an older one ignores the header). Path-matched on `/ocs/v2.php/apps/tickbuddy/api/` *anywhere* in the encoded path, because `BasicAuthInterceptor` runs first and may have prepended a subpath; `/cloud/capabilities` and `/cloud/user` don't get it. Reads carry it too, which is harmless.
- `OcsError.kt`: `ocsErrorMessage` (user-facing text) and `ocsErrorReason` (`ocs.data.reason`, Tickbuddy's machine-readable reason: `archived`, `trackNotFound`, …), both lenient. **Read an error body once** (`errorBody()?.string()` consumes it) and pass the string to both.
- `BasicAuthInterceptor` rewrites the host with the user's stored Nextcloud origin and adds the Basic auth header. On `401` it calls `AuthRepository.signOut()`.
  - **The rewrite must carry the origin's subpath**, via `encodedPath(serverUrl.encodedPath.trimEnd('/') + originalUrl.encodedPath)`. `TickbuddyApi`'s paths are absolute (`@GET("/ocs/v2.php/...")`), so they replace the path wholesale; setting only scheme/host/port — as it did until 1.0.6 — dropped the prefix from `https://example.com/nextcloud` on every API call. The failure was quiet and confusing because `AuthProber` builds URLs with `addPathSegments` and so *always* kept the subpath: the connect probe passed and then every real request went to the wrong place, failing in whatever way the host's root happens to answer. Subpaths are explicitly offered to users in `AuthViewModel`'s `NotNextcloud` message. A bare origin's `encodedPath` is `/`, which trims to empty and leaves the path untouched. Covered by three `BasicAuthInterceptorTest` cases (subpath, subpath + query, trailing slash) — the original tests only ever used a bare `host:port`, which is why this survived to release.
- `TickbuddyApi`: `getTracks(includeArchived?, includeAllTypes?)` (sends `includeArchived=true` only when `ServerFeatures.archivedTracks` is set; null leaves it out), `getTicks(from, to, includeAllTypes?)`, `toggleTick(trackId, date)`, `setTick(trackId, date, value)`, `setYesNo(trackId, date, value)` (the same `POST /ticks/set` with 1 or 0, a second method only because its answer is `TickYesNoResponse`, read leniently as 1/0 **or** `true`/`false`: Tickbuddy answered booleans before settling on 1/0 for 2.3.0), `incrementTick(trackId, date, delta, Idempotency-Key)` (`POST /ticks/increment`, `delta` never 0 — the server refuses 0 with a 400 + `reason`, which the push would drop), and the track calls `createTrack(name, type)`, `updateTrack(id, name? | private? | archived? + archivedAt?)` (one change per call; `archivedAt` is the phone's today, only with `archived=true`), `reorderTracks(trackIds[])`, `deleteTrack(id)`. The track calls are form-encoded exactly as Tickbuddy's own settings page sends them (`URLSearchParams`, `private=true|false`, repeated `trackIds[]`), so the server's parsing is proven. **Never send `sortOrder` on `PUT /tracks/{id}`**: the server has a unique index on `(user_id, sort_order)`, so a single-track move can collide; reorder is the only way order changes. `deleteTrack` returns `Response<Unit>` (204, no body). Server facts relied on: create ignores `private` (hence a second call), and a blank rename is an uncaught 500 (the UI never sends one).
- **Notes and stats calls** (`TickbuddyApi`): `getNotes(from, to, includeAllTypes)`, `setNote(trackId, date, text)` (never sent empty), `appendNote(trackId, date, text)` (no `allowDuplicate`: the push relies on the server skipping text already there as whole lines, so a lost append is safe to repeat), `deleteNote(trackId, date)` (`Response<Unit>`, 204; the push throws `HttpException(response)` itself when it isn't successful, so the drain's error handling applies), and `getStats(today)` (only `trackId`, `current {isStreak, length}`, `upToYesterday`, `maxValue` are read; no `includeAllTypes`, which stats doesn't define, so a track of a newer type may be missing — it then shows no streak).
- **`includeAllTypes=true` on every tracks, ticks and notes read** (pull, `changeTracks`' re-read, `TrackEditor.reorder`'s read, `pushBoolean`'s one-day read), with no capability flag. A Tickbuddy with types newer than yes/no and counter hides them from clients that don't ask (so Tickdroid 1.3.0 and older keep working); one without them ignores the parameter. The name follows Tickcli open decision 32; if that settles differently, change it here. The reorder read needs it too: `mergeOrder` drops ids the server didn't list, and the server puts unlisted tracks last.
- **`TickDto.value` is decoded leniently** (`LenientTickValueSerializer`): an integer as is; any other value becomes 1 if non-zero / non-empty (`7.5`, `"red"`, `true`, `{}`) and 0 otherwise (`null`, `false`, `0.0`, `""`). Without it one decimal tick of a future type fails the whole `GET /api/ticks` decode, and the `SerializationException` escapes `pull`. Only unknown-type tracks can hold such values, and their cells only use "above 0"; the 1 is a local marker the server never sees (those tracks never push). `TickValueResponse` stays strict: Tickdroid only writes known types. (`TickYesNoResponse` reuses the lenient serializer, see above.) Coverage: `TickDtoTest`, `SyncManagerPullTest.unknownType_…`.

**Repository**:

- `TrackRepository.observeTracks(): Flow<List<Track>>` — **active tracks only** (`TrackDao.observeActive`). That is what keeps archived tracks out of the journal, `WidgetRefresher` and widget setup with no change to them; anything new gets active tracks unless it asks otherwise. `observeAllTracks()` (archived included) is for Tracks settings and the track screen only. `findByServerId` returns archived tracks too, so `WidgetTickHandler` refuses `track.archived` as `TrackGone` (a widget drawn before the archive could otherwise tick one).
- `TickRepository.observeRange(from, to): Flow<Map<TickKey, Tick>>`
- `TickRepository.toggleBoolean(trackLocalId, date)` and `adjustCounter(trackLocalId, date, delta)` — wrap reads + writes in `db.withTransaction`, mark `dirty=1`, and enqueue a one-shot push. Pending-removal rows persist with `deleted=true` so the worker still sees them. **A tap never deletes a row; only the push does**, once the server has answered. Both used to delete a row whose `serverId` was null, taking that to mean "never reached the server" — but a push never fills in `serverId` (only a pull does), so unticking a day ticked more than 30 days back, or after a failed post-push pull, deleted it locally, sent nothing, and the tick came back at the next pull. So ticking and unticking before a push now sends one request (`set` to 0, or the read before toggle). `adjustCounter`'s arithmetic is the pure `counterTap` (`TickRepositoryMathTest`): it records the change the user **saw**, not the taps (−1 twice on 1 records −1; the value stops at 0, as the server's does), keeps a dirty absolute row absolute, and makes a row whose taps cancel out clean again (so the "unsaved changes" chip doesn't show for nothing) — unless it is at 0 (the push must delete it) or an increment awaits its answer (`sentKey`: the server may already have that delta, which the cancelling taps now have to undo).
- `NoteRepository.observeRange` (notes to show, by `TickKey`) and `saveNote(trackLocalId, date, raw)`: normalises, writes nothing when it equals what is shown, otherwise marks the row dirty with `baseText` = the clean row's text on the first change (kept on later ones), in `withTransactionUncancellable` (now a `TickdroidDatabase` extension in `TickRepository.kt`, shared by both repositories), then schedules a push. A save never makes a row clean or deletes one; only the push does.
- `TrackRunRepository.observeRuns()`: runs by track local id.
- `TickRepository.observeHasUnsent()` (was `observeHasDirty`): `TickDao` asks `EXISTS(dirty ticks) OR EXISTS(dirty notes)`, so an unsent note counts as an unsaved change. The Journal, Today **and `WidgetRefresher`** all use it, so the chip and the widgets' offline symbol keep agreeing.
- `TrackPrefsRepository.observeAll(): Flow<Map<Long, TrackPrefs>>`, plus `setColorKey`/`setEmoji`. Auto-deletes the row when both fields end up null.

## Sync layer

Implements `mobile_instructions.md` §4 with a few concrete tweaks captured below.

- **Pull** (`SyncManager.pull(from, to)`): `GET /api/tracks` + `GET /api/ticks?from&to`, then reconcile inside `db.withTransaction`. Server-authoritative when local rows aren't `dirty`. **`TickDao.getRange` includes rows marked `deleted`** (its only production caller is `reconcileTicks`): a queued untick was otherwise invisible to the reconcile, which then `upsert`ed the server's tick — `INSERT OR REPLACE` on the unique `(trackLocalId, date)` index — deleting the untick and storing the tick clean. A clean row marked deleted (older versions could leave one) is updated to the server's value with `deleted = false`, or deleted if the server has none. A pull still skips a dirty counter row; showing the server's value plus what's queued earlier was considered and left for later. **With `notes`**, the same pull reads `GET /api/notes` for the range (with the ticks, before the transaction) and `reconcileNotes` runs after `reconcileTicks` in the same transaction, mirroring it: new server notes inserted clean, clean rows take the server's text, dirty rows (and their `baseText`) are left alone, clean rows the server didn't return are deleted, notes of tracks not in Room skipped. Without the flag the notes table is untouched (a rolled-back server keeps the phone's notes queued). **With `stats`**, after that transaction and still in the lock, `refreshRuns` reads `GET /api/stats?today=<clock.today()>` and replaces `track_runs` in its own small transaction; **any failure but cancellation leaves the stored runs and the pull carries on** (as `refreshServerFeatures`), so a broken stats answer can never stop ticks syncing. `SyncManager` now gets the `Clock` injected. There is deliberately **no `deleteDirtyOfArchivedTracks` for notes**: an archived track's note write is answered 423 (dropped) or, by an older server, 200 with the stored note, which settles the row. Triggered on `JournalViewModel.refresh()` (which fires on `init` and `Lifecycle.Event.ON_RESUME`) and on pull-to-refresh.
- **Server features** (`ServerFeatures`, own SharedPreferences file `tickdroid_server_prefs`): the last-seen capability flags: `archivedTracks`, for the push `booleanSet`, `counterIncrement` and `idempotencyKey` (Tickbuddy 2.3.0), and `notes`, `notesAppend` and `stats`. Until the first pull after an update the push uses the old requests. A stale flag (a server rolled back) can't lose a tick: an older server answers `increment` with Nextcloud's own 404 and a yes/no `set` with a 400, neither carrying a `reason`, so both retry and the next pull refreshes the flags. Refreshed at the **start of every pull**, inside the lock and before the track read, so that read always matches the flag (one extra small `GET` per pull); the Account screen's fetch updates it too; cleared on sign-out. A failed or broken capabilities reply (anything but cancellation) leaves the stored value and the pull carries on. Later flags go in the same store: one `update(capability)`, one pure `…Flag()` helper and one `StateFlow` per flag, default false — no second call or cache.
- **Reading tracks**: `SyncManager.fetchTracks()` (adds `includeArchived=true` when the flag is set) and `applyTracks()` (`reconcileTracks`, which copies `archivedAt`, then `TickDao.deleteDirtyOfArchivedTracks`) are used by both `pull` and `changeTracks`, so they can't disagree. In `pull`, `applyTracks` runs before `reconcileTicks`, which then puts back the server's value for any dropped tick in the window. **Do not "simplify" the dirty-tick drop away**, even though a current Tickbuddy refuses such a tick with 423 and the push drops it (see "Push"): an older Tickbuddy still answers a tick on an archived track with a quiet 200 and the unchanged state, so `pushBoolean`'s toggle fallback leaves a yes/no tick dirty, and a track archived on *this* phone while a tick waits drops that tick only here, at the re-read; since archived tracks stay in Room, it would otherwise stay dirty for good — re-sent every push, never overwritten by a pull, the "unsaved changes" chip and the widgets' offline symbol stuck on while offline, and the old tick applied if the track is ever restored. `TrackEditor.reorder`'s own read is deliberately active-only (no `includeArchived`; it does send `includeAllTypes`): the server places unlisted tracks after the listed ones.
- **Push** (`PushWorker` + `SyncScheduler`). The paths below follow Tickbuddy's own `mobile_instructions.md` §4 and Tickcli; the flags come from `ServerFeatures`.
  - **Yes/no, with `booleanSet`**: one `POST /api/ticks/set value=1|0`, no read first. Safe to repeat. The server's answer wins (with `Prefer: handling=strict` it can only differ by a bug).
  - **Yes/no, without it** (2.2.0 and older): fetches one-day server state for `(trackId, date)` and only `POST /toggle` if it differs from the desired local state — the spec's replay-safety pattern. A toggle whose answer still differs leaves the row dirty for the pull.
  - **Counter with a known change (`pendingDelta` set), with `counterIncrement` and `idempotencyKey`**: `POST /api/ticks/increment delta=…` with an `Idempotency-Key` header ([draft-ietf-httpapi-idempotency-key-header](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header); a quoted UUID, i.e. a Structured Fields string, RFC 9651). The server adds it to whatever is there, so another device's or a script's change is kept, and its answer (which shows them) becomes the row's value. **`increment` isn't safe to repeat** — a lost answer to an applied increment would count twice on a retry (why Tickcli's `add` never retries, Tickcli decision 11) — so `claimIncrement` writes `sentKey` (a new UUID) and `sentDelta` (= `pendingDelta`) to Room **before** the request leaves, and every run resends exactly that key and delta until an answer arrives, whatever was tapped since (the draft forbids a key with a different body); the server answers a repeat as it answered the first. Taps made meanwhile go up in the request after it, with a new key. "No answer" is IO, TLS, any HTTP error `pushFailureFor` retries (a proxy's 502, Nextcloud's errors, Tickbuddy's 409 "still being handled"), or a cancelled worker. A refusal (423, 404/400/422 with a `reason`) drops the row with its key. Tickbuddy keeps keys 30 days, so a phone that loses an answer and then stays off longer could count it twice — accepted. `pendingDelta == 0` with no key sends nothing and just settles the row.
  - **Counter otherwise** — `pendingDelta == null` (queued before v4), or a server without both flags (a 2.3.0 pre-release has `counterIncrement` but not `idempotencyKey`) — `POST /api/ticks/set value=X` (X=0 deletes server-side). Idempotent. On an older server the `pendingDelta` bookkeeping carries on (and drops any key of a server rolled back since), so updating the server needs nothing from the phone.
  - **Re-read, then settle (do not regress).** `drain()`'s `getDirty()` snapshot only gives the order: each row is re-read by `localId` (`TickDao.findById`) just before it is sent and skipped if it's gone or clean, and the answer is applied by a settle step that re-reads it again, in one transaction (under `NonCancellable`, so an answer that arrived is recorded even while the worker is stopped). Taps don't take the sync lock, and the old `finalize` wrote the snapshot back marked clean, so a tap made while a request was on the wire was overwritten and never sent (quick taps on a counter lost one). `settleYesNo` leaves a row whose desired state changed during the request dirty for the next run; `settleAbsolute` settles only a row whose value, `deleted` and null `pendingDelta` are unchanged; `settleDelta(sent, serverValue)` keeps `pendingDelta − sent` pending on top of the server's value (dirty), or settles clean when nothing remains. All three delete the row when the server's value is 0.
  - **A track of an unknown type** (`TrackType.Unknown`; `PushWorker` maps through `TrackType.fromWire`, there is no second mapping): the tick is deleted unsent with a `Log.w`, and the queue carries on. Only a bug can queue one (taps never write), but left dirty it would keep the "unsaved changes" chip on for good. Before this, anything that wasn't `counter` was pushed as a toggle.
  - **After an HTTP error on one row** (pure `pushFailureFor(code, reason)`, `PushFailureTest`): `401` → sign out, `Result.failure()`, no retry. `423` → drop that tick (`deleteById`), carry on with the queue, note a refusal. `404` / `400` / `422` **carrying a Tickbuddy `reason`** (track deleted elsewhere, a bad value; 422 is `idempotencyKeyReused`, which only a bug here can cause, and is logged) → drop it silently and carry on. **Anything else** — `404` / `400` without a reason, other 4xx, 5xx, IO, TLS → stop and `Result.retry()` with exponential backoff, as before. **Do not drop on a bare 404**: Nextcloud answers 404 for every Tickbuddy URL while the app is disabled (a Nextcloud upgrade does that to apps not yet marked compatible), so it would silently lose the whole queue; Nextcloud's, a proxy's and older Tickbuddys' errors never carry a `reason`. 423 is read as "archived track" only because every call the drain makes is to Tickbuddy's own API. Worker constraint: `NetworkType.CONNECTED`.
  - **Notes** go after the ticks in the same `drain()`, under the same lock (`noteDao.getDirty()`, only with `notes`; without it they stay queued, decision 16k). The early "nothing dirty" return looks at both. Each row is re-read by `localId`; skipped if its track has no `serverId`. Then: **read** the server's note for the day (`getNotes(date, date)`), **plan** with the pure `planNotePush(phone, base, server, canAppend)` (`domain/NoteText.kt`, `NoteTextTest`) — `Settle` when the server already has the phone's text; the phone's version (`Set`, or `Delete` when empty) when the server's note equals `baseText` or there is no `notesAppend`; otherwise `Append` of the phone's **new lines** (non-blank, in neither base nor server, phone's order, each once — an edited line goes up in its new form and the old stays, a removed line stays), `Settle(server)` when there are none, or `TooLong` when `server + "\n" + lines` would pass 500 code points (nothing sent, row settled to the server's note, and "The note for *X* would be longer than 500 characters, so the change wasn't saved." after the pull, once per track) — then **settle** (`settleNote`, re-read in one `NonCancellable` transaction): a row still holding the sent text goes clean at the answer (or is deleted at `""`); a row **edited during the request** stays dirty with its new text, and its `baseText` becomes the answer only if the server now holds exactly what was sent (otherwise unchanged, so the next run merges again). Errors go through the same `send()` as ticks (one function, both loops): 423 drops the note and shares `noteRefusal`'s once-per-track notice with ticks; 404/400/422 with a `reason` drop silently (`Log.w` for 400/422); 409 `noteConflict`, IO, TLS and the rest retry. **Accepted gap**: between the read and a `set`/`DELETE`, another writer's change is overwritten — Tickbuddy has no conditional write for notes.
  - **A run with drops still pulls** (the drain finished), so a track deleted elsewhere leaves Room, and the widgets, in that same sync; the pull puts back the server's value for a dropped day in the 30-day window.
  - **`PushNotices`** (an `open` `@Singleton`, like `SyncScheduler`, so `PushWorkerTest` records instead of toasting): each 423 adds "*Track name* is archived, so the change wasn't saved." (name from Room) — or for a `reason` other than `archived`, the server's own `message`, if any — **once per track per run**, in queue order (`getDirty` is `ORDER BY localId`). They are shown as `LENGTH_LONG` toasts from the worker, over whatever is on screen (allowed from the background on Android 12+, so widget-only users see them), **after the pull**, and **also after a `Retry`** (the refused rows are gone, so a later run would never mention them), but not after a 401. A run cancelled between drop and toast loses the toast; accepted.
- **Online state** (`NetworkMonitor.isOnline`): follows the **default** network via `registerDefaultNetworkCallback`; online = it has `NET_CAPABILITY_INTERNET` (not `VALIDATED`, by decision — a captive portal still counts as online). One synchronous read before registering gives the initial value; after that the state comes **only from the callbacks' own arguments**, through the pure `DefaultNetworkTracker` (only `onLost` of the *current* default means offline, so a Wi‑Fi ↔ mobile switch works in either callback order). **Never read `activeNetwork` or `getNetworkCapabilities` inside a callback**: in `onLost` it can still return the network being lost, which (until after 1.2.0) re-emitted `true`, and with no network left nothing called back again — every collector stuck "online" until its `WhileSubscribed(5_000)` lapsed. Coverage: `DefaultNetworkTrackerTest`.
- **Push/pull mutex**: `SyncManager.mutex` is held by `pull()` (around network + reconcile) and by `PushWorker.drain()` via `SyncManager.runExclusive`. Prevents the snapshot-then-stomp race where a concurrent pull would drop a row that a push had just cleared.
- **Triggers**:
  - One-shot `OneTimeWorkRequest` after every local write — `ExistingWorkPolicy.APPEND_OR_REPLACE` so a burst of taps coalesces a follow-up instead of cancelling the running drain. **Expedited** (`RUN_AS_NON_EXPEDITED_WORK_REQUEST` past quota): once the app is frozen in the background (the OS also freezes its `NetworkCallback`s, so `NetworkMonitor` goes blind), this job is the only thing that wakes it when the network returns. As an ordinary job it was batched on battery — measured on a Samsung S23 / Android 16 on mobile data: held 45–50 s, up to 4 min by its `sec_conn_max_connectivity_job_batch_delay_ms`, longer in Doze — and the widgets' offline symbol stayed up all that time. Batching is off while charging and on Wi‑Fi, so tests over USB never see it.
  - Periodic `PeriodicWorkRequest` every 15 min while signed in.
  - `PushWorker.doWork()` is push-then-pull: drain under the mutex, and on success call `SyncManager.pull(today − 30d, today)` so periodic background work also surfaces changes from other devices.
- **Coroutine scoping (do not regress)**: sync is *application* work, never UI work. `SyncManager.schedulePull` runs pulls on `SyncManager`'s own application-lifetime scope; UI must call that rather than `viewModelScope.launch { pull(...) }` (`PushWorker` still awaits `pull` directly — it has to, to report its `Result`). Room reacts to a cancelled transaction caller by closing the pooled connection while the block is still running on its own executor thread, so the next statement throws `SQLITE_MISUSE` ("connection is closed") on a thread with no cancellation handling — an uncaught fatal, not a `CancellationException`. Belt-and-braces, the reconcile in `pull` and both write paths in `TickRepository` run under `NonCancellable`. Regression coverage: `SyncCancellationTest`.
- **Lifecycle**: `SyncCoordinator` (started from `TickdroidApplication.onCreate`) collects `AuthRepository.state`. On sign-in: schedule periodic + kick a one-shot. On sign-out (only when transitioning from `SignedIn`, never on the initial fresh-install `SignedOut`): cancel both + `clearAllTables()` (under `runExclusive`, and never `close()` — see "Scope decisions") + reset `UiPreferences` + clear `WidgetConfigStore` (widgets then redraw on their own, via `WidgetRefresher`).
- **Cancellation restores the status (do not regress).** `PushWorker.drain` and `SyncManager.pull` set `Pushing` / `Syncing` before going to the network, and their catches only handle HTTP / TLS / IO errors. A `CancellationException` (WorkManager stopping the worker, typically because JobScheduler's network constraint failed when the network lost validation) used to slip past them and leave the status stuck for the rest of the process: the journal's chip vanished (`computeSyncIssue` ignores a push in flight), its spinner could spin forever, and the widgets showed a dead faded ⟳ instead of the offline symbol. Both now catch `CancellationException`, put back the status from before the attempt (an interrupted attempt says nothing new about the server), and rethrow. Coverage: `PushWorkerTest.cancelledMidPush_restoresThePreviousStatus`, `SyncCancellationTest.cancelledPull_restoresThePreviousStatus` (both fail with the stuck state if the catch is removed).
- **Track changes** (`SyncManager.changeTracks`, used only by `TrackEditor`): runs the change under `mutex`, then re-reads `GET /api/tracks` and runs the existing `reconcileTracks` under `NonCancellable` — all in **one hold** of the lock, so a pull can't reconcile half-way through a change. It can't call `pull()` for the re-read: `pull` takes the mutex itself and `Mutex` isn't reentrant. It runs on `SyncManager`'s application scope (`scope.async { … }.await()`), for the same reason as `schedulePull`: Back pressed mid-save must not cancel a Room transaction. The re-read happens even after a failed change (a timed-out create may have landed), is skipped once a 401 has signed out, and a failed re-read never hides the change's outcome (Room catches up at the next pull). It deliberately leaves `status` / `pushStatus` alone: a track change is not a sync. `reconcileTracks` updates by `serverId`, so renames and reorders keep `localId` (the track screen's nav argument); a delete cascades the track's ticks, dirty ones included, which is right because the server deleted them too.
- **`TrackEditor`** (`archive(serverId)` sends `archived=true` + `archivedAt = clock.today()`; `restore(serverId)` sends `archived=false`; a 404 on either shows the server's "Track not found", unlike delete) validates names (`cleanTrackName`: trimmed, 1–255 code points), runs each change through `changeTracks`, and maps exceptions to a `TrackChange` (`Done` / `Created(serverId)` / `CreatedNotPrivate` / `Failed(message)` / `SignedOut`), so ViewModels never see Retrofit or IO types. Mapping order as in the rest of the sync layer: `SSLException` before `IOException`, by type never message; 401 → `SignedOut` (the interceptor already signed out); 404 on delete → `Done`; 423 with `reason: "archived"` on **archive** → `Done` (archived elsewhere while the track screen was open: the list opens Archived with the track in view, and the track keeps the other device's date); any other 423 (rename, Private, reorder on a track archived elsewhere) is an ordinary refusal; otherwise the server's `ocs.data.message` / `ocs.meta.message` (`ocsErrorMessage`, lenient — `data` is `[]` for a thrown `OCSException`, and proxies send HTML), else "…returned an error (HTTP n)". **Reorder re-reads the server's ids inside the same hold and sends `mergeOrder(wanted, serverOrder)`**: `PUT /reorder` makes every sort order negative and then numbers only the listed ids, so a track added on another device since the last pull would otherwise keep a negative sort order and jump to the top; ids deleted elsewhere are dropped.
- **Status surfacing**: `SyncManager` exposes `status: StateFlow<SyncStatus>` (pull) and `pushStatus: StateFlow<PushStatus>`, both of which carry a `SyncErrorKind` (`ServerUnreachable` / `UntrustedCertificate` / `ServerError`) when in `Error`. `JournalViewModel` combines those with `NetworkMonitor.isOnline` and `TickRepository.observeHasDirty()` into a `SyncIssue` (`Offline` / `ServerUnreachable` / `UntrustedCertificate` / `ServerError` / `None`, each tagged with `hasUnsavedChanges`). The top bar shows a `CircularProgressIndicator` during pull and a tonal `AssistChip` (`errorContainer` colors, `CloudOff` icon) whose label varies: "Offline" / "Server unreachable" / "Certificate not trusted" / "Sync error", optionally suffixed with ", unsaved changes". Both `when` blocks in `SyncIssue.kt` are exhaustive, so adding a kind is compiler-guided.

- **Day-by-day scrolling: two snapping `LazyRow`s, one vertical scroll.** The day columns are a `LazyRow` of one-slot items with `rememberSnapFlingBehavior(listState, SnapPosition.Start)`: a fling travels freely, a slow drag settles on the closest column edge, and the leftmost column always ends up flush with the name column. A sticky header row (range label + a second `LazyRow`, `userScrollEnabled = false`) sits above a `verticalScroll` `Column` holding the name column and the day columns. The body drives; the header follows via a `snapshotFlow` on `firstVisibleItemIndex`/`firstVisibleItemScrollOffset`. **Use `requestScrollToItem`, not `scrollToItem`, for the follow**: the body updates its position during measure, the collector can resume mid-layout, and the suspending scroll forces a remeasure, giving `IllegalArgumentException: performMeasureAndLayout called during measure layout` (caught by `TracksDownGridTest`). **Not a `HorizontalPager` with one-slot pages**, though that was the first version (and what an earlier spec preferred): on a slow release the pager chooses its target from the finger's travel in whole pages (`PagerSnapLayoutInfoProvider`, decimal part of `upDownDifference / pageSize`), and with pages this small the touch slop (~20% of a column) makes that disagree with the real scroll. A slow one-column drag snapped *back*, 1.6 columns jumped 2. LazyRow snapping picks the closest edge by actual position. Track rows are not a `LazyColumn` (track counts are small).
- **Uniform row height.** Labels show the emoji plus the full name, wrapping to two lines and then ellipsizing; **at High density names stay on one line** (ellipsized), so rows stay one cell tall. **Words are never split across lines**: Android's line breaker has no such mode, so `splitLabel` (pure, JVM-tested) puts as many whole words on line 1 as fit — measured with a `TextMeasurer` against the width from `BoxWithConstraints` — and the rest on line 2, and each line renders single-line with an ellipsis. A word too wide for a line becomes "Exerc…" rather than "Exercis / e". Semantics carry the full name as one text node. (Hyphenation was tried and dropped — it looked messy in practice.) a row is at least `cellSize + CellGap` tall and grows to fit a wrapped name, with its cells centred in the taller slot. Because label column and pager are separate children, the body row is a `SubcomposeLayout` that measures the labels first (at the label column's real width) and passes the resulting row heights to the pager. A plain `Row` can't do this: it measures the fixed-width pager *before* the weighted label column. Placement uses `placeRelative` so RTL still mirrors. Covered by `TracksDownGridTest.longName_wrapsAndGrowsRow_cellsStayAligned`. Every row gets one height: one cell row (`cellSize + CellGap`) normally, or the tallest label's height if any name wraps, so the grid stays even. The labels are centred in that height, like the cells. Because the name column and day columns are separate children, the body row is a `SubcomposeLayout` that measures the labels first (at the name column's real width) and passes the height to the columns. A plain `Row` can't do this: it measures the fixed-width columns *before* the weighted name column. Placement uses `placeRelative` so RTL still mirrors.
- **Columns anchored on today, newest first.** Column *i* is `today − i` (`dayForColumn`); column 0 is **today, leftmost** (its header reads "Today" in place of the weekday letter), going back in time to the right. Not calendar weeks (avoids the Nextcloud-vs-locale first-day-of-week mismatch). Swiping left goes back in time; Compose mirrors the lists under RTL. The header's range label shows the days in view (`daysInView(firstVisibleItemIndex, N, today)`, read via `derivedStateOf` so it recomposes once per column, not per frame).
- **Slot sizing** (`tracksDownMetrics`): up to `GridSizingMaxWidth`, the track-label column gets a fixed 36% share of it (`NameColumnFraction`, ~148dp on a 411dp Pixel 6a — enough for an emoji plus a typical name on one line), and the rest minus `RightPad` is split into N touching slots with the `TickCell` centred at `slot − CellGap`. N (columns visible) comes from `GridDensity.tracksDownDays` (Low 5 / Medium 6 / High 8 — deliberately not Days down's 5 / 7 / 9: Medium at 6 keeps cells at their Days-down size, ~35dp, on the 6a instead of squeezing 7 in at ~29dp), capped by how many 28dp cells fit and floored at 3. So High shows 7 on the 6a and 6 at 360dp. **Beyond the 480dp cap (landscape, tablets) the extra width becomes extra days**, not a wider label column: slot and label sizes stay what the cap gives (its "portrait-equivalent" size, as in Days down) and N = however many columns fit, e.g. 13 days at Medium on a Pixel 6a in landscape, with cells at ~42dp. So in landscape density sets the cell size, not the day count. (Originally the extra went to the label column, which left a ~600dp mostly empty name column.) Sizing uses the grid's measured width via `BoxWithConstraints`, **not** `Configuration.screenWidthDp`: with targetSdk 35+ the latter includes the display cutout, which in landscape would overflow the day columns. No half-cell peek: columns snap, so none is ever cut off. (The label used to get only what the slots left over, which bottomed out at a 104dp minimum and wrapped almost every name that had an emoji.)
- **History.** The list holds exactly the loaded `DateWindow` (`columnCount`), so it can't scroll onto unpulled days. Mirroring Days down's `nearBottom`: when `firstVisibleItemIndex + N >= count − 7`, `loadOlder()` adds 30 days. The effect is keyed on `nearEnd` **and** `count`, because after a long fling one extension may leave `nearEnd` still true, and an unchanged key alone wouldn't re-run it.
- **Keeping position needs no code.** Column indices don't depend on N, so a rotation or density change keeps the same leftmost day (the saveable `LazyListState` holds the index). This replaced the paged version's anchor logic, which drifted a page towards today on a rotate-there-and-back. Midnight rollover shifts everything one column (column 0 is the new today). Switching layout in settings starts on today.
- **Test hooks**: `testTag("tracksDownGrid")` on the day-column `LazyRow`, `"cell-<localId>-<epochDay>"` on each cell slot, `"label-<localId>"` on each name label, `"rangeLabel"`, `"jumpToToday"` on the chip. Bounds checks in tests must use *unclipped* bounds, and skip NaN: off-screen cells otherwise report bounds clipped to the list's edge.

### Navigation
- **Today is the start destination when signed in** (`Routes.TODAY`, still frozen with `remember`), and `SyncNavToAuthState`'s signed-in target, so TODAY is always the root of the back stack while signed in. **The bar navigates with `openTab(route)`**: `popUpTo(Routes.TODAY) { saveState = true }`, `launchSingleTop`, `restoreState` — the standard bottom-nav pattern, which keeps the Journal's layout, scroll and loaded days. **Pop by route, never `graph.startDestinationId`** (frozen at AUTH after a sign-in, so popping it would be a no-op — the same trap as below). The Journal's Back is a `BackHandler` calling `openTab(TODAY)` (a plain pop would discard its saved state). Bar Today and day labels write `openFromJournal` then `openDay` (epoch day) into TODAY's own entry's `savedStateHandle` (the `JUST_ARCHIVED` pattern), and `TodayScreen` applies and clears them; with `fromJournal`, a `BackHandler` returns to the Journal. Sign-out also `clearBackStack(Routes.JOURNAL)` so the next account doesn't restore the last one's Journal.
- **`MainActivity` is `adjustResize`** (manifest, `windowSoftInputMode`; do not remove). With edge-to-edge that means the window is neither panned nor resized and the keyboard reaches Compose only as `WindowInsets.ime`. Left unset, Android picked `adjust=pan` (seen in `dumpsys window`): it panned the whole window up while the note card lifted itself above the keyboard with its `ime` padding, so the card opened at the top of the screen, half off it, until the first key press made Android drop the pan (Samsung S23, release build, 29 Oct).
- **`MainActivity` is `singleTop`** (manifest). Widgets open the app with Glance's `actionStartActivity<MainActivity>()` and setup's "Open Tickdroid" with `FLAG_ACTIVITY_NEW_TASK`; without a launch mode each such tap stacked a second `MainActivity` (Back first showed the old copy). With a single activity in its task, a new start now reaches the existing one (`onNewIntent`, nothing to handle), screen intact. Verify with `adb shell dumpsys activity activities | grep -i tickdroid` (exactly one `MainActivity`).
- **One driver for auth transitions.** `NavHost`'s `startDestination` is captured once via `remember` and must *not* be derived from a changing `authState`: `NavHost` rebuilds its graph whenever `startDestination` changes, and `NavController.setGraph` pops the entire back stack when handed a new graph instance, destroying the current destination's `ViewModelStore`. With both that and `SyncNavToAuthState` reacting to the same state, first sign-in tore down `JournalViewModel` mid-pull and crashed the process (see "Coroutine scoping"). `SyncNavToAuthState` is the sole driver; `startDestination` only picks the entry point. Freezing it is safe because `AuthRepository` resolves real state in its constructor, so a returning user's first composition already reads `SignedIn`.
- **Pop the whole graph, never the start destination.** `SyncNavToAuthState` uses `popUpTo(navController.graph.id) { inclusive = true }`. It must not use `graph.startDestinationId`: now that the start destination is frozen at the process's initial auth state, it no longer tracks where the user is, and `popUpTo` on a destination that isn't on the back stack is a silent no-op. That left the previous screen and its ViewModel alive underneath the new one — so after sign-out → sign-in → sign-out the login screen came back pre-filled with the previous session's server, user and **app password** (revealable via the eye toggle), and `AUTH` sat under `JOURNAL` so Back from the journal landed on the login screen while signed in. Note `remember` is not `rememberSaveable`, so the frozen value re-evaluates after a configuration change — another reason nothing may depend on `startDestinationId` being current.

## Home-screen widgets

Three Glance widgets in package `widget`, all ticking **today only** (whatever Editable days says) and never showing private tracks (whatever "Show private tracks" says). Spec decisions are in the widgets implementation spec (2026-10-06); this is how they're built.

- **Unknown-type tracks** are offered and drawn like any other, read-only: "?" on the ticked colour when above 0, the plain empty cell otherwise, `ReadOnlyTapAction` on tap (see "Scope decisions").
- **Archived tracks** never reach the widgets (`observeTracks()` is active-only): lists and rows drop them, a Single track widget for one shows its "Choose track" tile, and a restore brings both back (config is by server id).
- **Kinds**: *Single track* (1×1, `SizeMode.Single`: one track's cell, labelled with the shared `ShortLabel` — emoji or two-letter abbreviation, as in the Today row — tap toggles / adds 1; "?" tile with "Choose track" or "Signed out" text when there's no track), *Today list* (`SizeMode.Exact`, resizable to 2×2: header + `LazyColumn` of rows, whole row is the tap target, Full / Icon track labels per widget — "Icon" is `TrackLabels.Short`, renamed on screen only because the enum name is what `WidgetConfigStore` saves), *Today row* (`SizeMode.Exact`, 4×1 default: Days-down-style columns, tracks that don't fit are left out from the end via pure `rowCapacity`). No widget can subtract from a counter; that's done in the app.
- **One write path.** Every tap is an `ActionCallback` → `WidgetTickHandler.onTap` → `TickRepository.toggleBoolean` / `adjustCounter` — the journal's own transactional, dirty-bit, push-on-write path, so widget taps work offline and sync identically. The tap carries the epoch day the widget was **drawn for**; anything but `clock.today()` is refused (`StaleDay`: redraw + Toast "New day: tap again to tick"), so a late midnight alarm or a time-zone change can never put a tick on the wrong day.
- **Config**: `WidgetConfigStore`, its own SharedPreferences file `tickdroid_widget_prefs`, JSON per `appWidgetId`, tracks referenced by **server id** (local ids don't survive a re-pull). Tracks a list/row's map doesn't mention are shown, so new tracks appear automatically. Not in Room (would need schema v3 + a `Migration` for per-device UI state), not Glance state (can't be cleared in one call on sign-out). Cleared on sign-out, entries removed in `onDeleted`.
- **`WidgetRefresher` is the single redraw hook.** An application-scope `combine` over auth, tracks, prefs, today's ticks, sync status (`computeSyncIssue`, so the widgets' offline symbol and the journal chip always agree) and the store's `revision`, held in a `StateFlow` (equal data — e.g. a pull that rewrote unchanged rows — doesn't redraw) and debounced into `updateAll`. That covers journal taps, widget taps, PushWorker, PTR, emoji/colour edits and the sign-out wipe with no change to the sync layer.
- **Widgets collect `WidgetRefresher.inputs` inside the composition — do not "simplify" this to a snapshot loaded in `provideGlance`.** While a Glance session is alive (up to ~45 s after its last update), `update()` only sends `UpdateGlanceState` and recomposes; it does **not** re-run `provideGlance`. A one-off snapshot would keep drawing the pre-tap state after the very tap that changed it. The collector lives only as long as Glance's session. **The converse matters just as much: `WidgetRefresher`'s `updateAll` on every change is not redundant with that collector.** Most of the time a widget's session has closed, nothing is collecting, and only `update()` starts a new session to redraw it. Both halves are needed.
- **Day changes**: an inexact, non-wakeup `AlarmManager.setAndAllowWhileIdle(RTC, …)` for 00:01 (pure `nextRolloverMillis`, DST-safe) plus `TIME_SET` / `TIMEZONE_CHANGED`, all to `WidgetRolloverReceiver` (exported for the system broadcasts; it only redraws and re-arms). Armed only while a widget is placed. No exact-alarm permission and no battery-exemption request, by decision: the stale-day guard makes a late redraw harmless.
- **Setup runs in its own task.** `WidgetConfigActivity` has `android:taskAffinity=""` (plus `excludeFromRecents`). With the app's default affinity, ✎ → Save finished it back into Tickdroid's task and surfaced the journal instead of the home screen. Its "Open Tickdroid" button therefore starts `MainActivity` with `FLAG_ACTIVITY_NEW_TASK`, so the journal lands in the app's own task.
- **"Add widget" vs "Save" in setup** is not "is a setup stored?": a placed widget can have none (sign-out clears every widget's choices but keeps the widgets), and its first ✎ then read "Add widget". Intents from a placed widget (`configIntent`: ✎, "Choose tracks", "Choose track") carry `EXTRA_FROM_WIDGET`; setup reads "Save" if that is set **or** a setup is stored, so only the launcher placing a new widget gets "Add widget". Covered by `WidgetConfigViewModelTest`.
- **Unsent notes count**: the offline symbol uses `observeHasUnsent`, so an unsent note shows it just as an unsent tick does. Nothing else about notes reaches the widgets.
- **Sync slot** (list header, Today row): faded ⟳ with no action while syncing, else the cloud-off symbol in ⟳'s place while unsent ticks can't go up, else ⟳. The Single track's corner badge uses the same rule (`badge.slot == SyncSlot.Offline`, so it also hides while syncing); all three kinds must agree on when the symbol shows. Both ⟳ and the symbol run `RefreshAction` → `SyncScheduler.schedulePushNow()` (the existing push-then-pull worker), never a pull from the broadcast.
- **Background** (per widget: Solid | Translucent | Transparent, a segmented row in setup; brief of 23 Oct 2026). Stored as a **percentage**, `WidgetConfig.background` (100 / 50 / 0, default 100, so a setup saved before it existed — and every widget after sign-out — is Solid), so a slider could replace the three choices without changing what is saved; read through `backgroundPercent()`, which clamps, and setup selects the choice nearest the stored value. `provideWidgetContent` provides it as `LocalWidgetBackground` (default 100, which is why the widget tests draw Solid without providing it). Every root is `WidgetSurface`: at 100 it keeps today's exact `.background(widgetBackground)`; below that, `.background()` can't help — `widgetBackground` is, on Android 12+, a resource colour that follows the wallpaper and is resolved by RemoteViews, so it can't take an alpha — and `BackgroundLayer` draws `widget_background_fill` (a white shape) tinted with it at the alpha, the faint dot's mechanism, clipped by the root's corner radius; at 0 there is no layer but the root keeps `appWidgetBackground()`. Padding belongs on the content inside the surface, never on the root, or the layer is inset too (Today row). Empty cells (dot, counter 0, the "?" tile) draw at `emptyCellAlpha` = `max(background, 60)%`; ticked cells keep full colour. Single track's offline-badge disc follows the background the same three ways. On Transparent text is only as readable as the wallpaper; accepted, and setup says nothing about it. Single track setup **picks, then saves**: a tap moves the ✓, "Add widget" / "Save" at the bottom is disabled until an offered track is picked (`chosenServerId` is null for a stored track that's no longer offered). **Segment labels** (`SegmentLabel`, shared by Background and Track labels): one line, `autoSize` from the button's `labelLarge` down to 11sp (`labelSmall`), then an ellipsis. **material3 1.4's `SegmentedButton` measures its label at the segment's full width and only then puts the ✓ before it**, so a selected label that fills the width ran under the button's edge, and autoSize, seeing only that width, never shrank it. So a selected label measures itself narrower by `SegmentedButtonDefaults.IconSize` + 8dp (the button's private `IconSpacing`) — in a `Modifier.layout`, **not** `BoxWithConstraints`: the segmented row asks for intrinsic sizes, which a `SubcomposeLayout` refuses, crashing setup on open. On a 360dp phone at normal font size the selected "Translucent" / "Transparent" therefore reads "Transluc…" / "Transpar…"; keeping the ✓ over fitting the word was Martin's call (23 Oct). `SegmentLabelTest` checks every label stays inside its segment's content padding at 320 / 360 / 411dp × font scale 1 / 1.3 / 2, each choice selected.
- **Colours**: `GlanceTheme` defaults (live Material You system colours) except the empty cell, which is the journal's `surfaceContainerHighest` read from `dynamicLight/DarkColorScheme` — Glance's colour set has no such role. That one colour is fixed at draw time, so after a wallpaper change it catches up on the next redraw. Emoji are full colour, as in the app.
- **RemoteViews limits**: containers take at most 10 children (Glance silently drops the rest), so Today row columns go in nested `Row`s of 8. No SemiBold and no `tnum` in RemoteViews text; cells use Medium.
- **Tests**: pure maths/models on the JVM (`WidgetModelsTest`, `WidgetRolloverTest`, `WidgetConfigCodecTest`, `WidgetTickHandlerTest`); Glance node tests per kind (`runGlanceAppWidgetUnitTest`); `WidgetRemoteViewsTest`, which runs every state through Glance's real RemoteViews translation (`GlanceAppWidget.compose`) and inflates it — flip its `DUMP` flag to write PNGs for a visual check (`backgrounds_allKinds` renders every kind at 100 / 50 / 0, light and dark; `connectedDebugAndroidTest` uninstalls the app afterwards, taking the PNGs with it, so for the PNGs run the class with `adb shell am instrument` after `installDebug installDebugAndroidTest`). Each kind's node test checks that only Translucent has the `widgetBackgroundLayer`. Inflate under an `AppWidgetHostView`: the platform only installs collection adapters (the list's rows) under one, so a plain `FrameLayout` silently renders an empty list. `WidgetTickHandlerIntegrationTest` proves a widget tap leaves a dirty row and schedules one push.

## Tech debt / known limitations

Tracked from a code audit at the end of Phase 3. Items marked ✅ have been addressed; the rest are open.

1. ✅ Race-free local writes: `TickRepository` wraps read-modify-write in `db.withTransaction`.
2. ✅ Work scheduling: `OneTimeWorkRequest` uses `APPEND_OR_REPLACE` so a tap stream doesn't cancel the running drain.
3. ✅ Pull/push serialization via `SyncManager.mutex`.
4. ✅ **Periodic work also pulls.** `PushWorker.doWork()` runs the drain under the sync mutex, then (only on success) calls `SyncManager.pull(today − 30d, today)`. So the same 15-minute periodic worker now both pushes dirty rows and refreshes recent history; the journal's pull-on-resume / PTR still covers older windows.
5. ✅ Midnight rollover: `JournalViewModel` recomputes `today` on every `refresh()`, and `JournalScreen` calls `refresh()` from `LifecycleEventEffect(ON_RESUME)`.
6. ✅ Push errors visible: `PushStatus` flow + top-bar `SyncIssueChip` (six labels covering offline / server unreachable / server error × dirty-or-not).
7. ✅ **Destructive fallback removed.** (v2→v3 shipped with `MIGRATION_2_3` and `MigrationTest`, as below.) `DatabaseModule` no longer calls `fallbackToDestructiveMigration()`, and `@Database(exportSchema = true)` writes per-version JSON to `app/schemas/` (checked into git). Any future schema bump (v2→v3 etc.) must ship with a `Migration` added via `.addMigrations(...)`, plus a `MigrationTestHelper` test replaying the previous schema. Without one, the app will crash at startup rather than silently wipe user data.
8. ✅ **`UiPreferences` reset on sign-out.** `SyncCoordinator` calls `UiPreferences.clear()` and `WidgetConfigStore.clear()` alongside `database.clearAllTables()`, so theme, density, journal layout, editable-days, and show-private all return to defaults, and every widget's choices are forgotten. Still device-wide rather than user-scoped — if multi-account-on-one-device becomes a goal, scope by `(serverUrl, login)`.
9. ✅ **Orphan `TrackPrefs` rows swept on pull.** `SyncManager.reconcileTracks` deletes any `track_prefs` row whose `serverId` is no longer in the server's response, alongside the corresponding track deletion. `track_prefs` is local-only so there's nothing to push.
10. ✅ **Tests landed in Phase 5.** 63 JVM unit tests + 62 instrumentation tests covering: repositories (transactional writes, dirty-bit lifecycle), sync conflict matrix (pull reconciles, push replay-safety, push/pull mutex, sign-out wipe), OCS envelope + headers + basic-auth interceptor + auth prober, the journal `TickCell` tap/long-press UX, and the "Tracks down" layout (pure sizing/paging maths on the JVM, `TracksDownGridTest` for paging and taps). The Compose UI coverage stops at `TickCell` rather than the full `JournalScreen` — see "Future considerations".
11. ✅ **Subpath server URLs fixed.** `BasicAuthInterceptor` now prepends the stored origin's path (see "Network"), with three regression tests. Found while investigating an unrelated crash; it had never been exercised because every existing test used a bare `host:port`.

## Future considerations (not on the critical path)

Items consciously deferred. Revisit when product priorities shift or when external factors (e.g. AndroidX replacement landing stable) force a decision.

- **Tap targets <48dp at high density.** `MinCellSize = 28dp` falls below Material's 48dp guideline at the High density setting. Mitigations: bump `MinCellSize`, or expand the click area beyond the visible cell via `Modifier.minimumInteractiveComponentSize` / a transparent padded hitbox. Acceptable for v1 as a power-user trade-off.
- **Hardcoded strings everywhere.** No `strings.xml`, no localization. Single-locale (English) is fine for v1; revisit if localization becomes a goal.
- **Trust-on-first-use certificate approval.** `<certificates src="user"/>` (see "Scope decisions") grants trust app-wide over the *whole* user CA store — a CA installed years ago for mitmproxy or a corporate MDM can also intercept Tickdroid traffic. The stronger model, used by the Nextcloud Android client, is to show the certificate on handshake failure (subject, issuer, validity, SHA-256) and let the user approve *that* certificate into an app-local keystore. Needs a custom `X509TrustManager` wired into all three OkHttp clients (`NetworkModule`'s singleton plus `AuthProber`'s two, which it builds itself — so a seam is needed), a persistent keystore, approval UI, a retry-after-approval flow inside the suspend probe, and a settings screen to review/revoke. Nextcloud's own dialog has a crash history ([#10871](https://github.com/nextcloud/android/issues/10871), [#11677](https://github.com/nextcloud/android/issues/11677)) — the design is right, the implementation needs care. If it lands, `src="user"` can be dropped or kept as a fallback.
- **Nextcloud Single-Sign-On.** [`nextcloud/Android-SingleSignOn`](https://github.com/nextcloud/Android-SingleSignOn) lets a companion app borrow the account already configured in the official Nextcloud Android client via an AIDL binding, instead of asking the user to paste an app password. Two things make it interesting here: it would supersede the pasted-app-password flow (and retire the `beginLoginFlowV2()` stub), and — because requests are proxied through the Nextcloud app — it inherits that app's TLS trust, including any self-signed certificate the user has already approved there. That is a free fix for [#37](https://github.com/martinhammer/tickdroid/issues/37) for anyone running the Nextcloud app. Costs: a hard dependency on that app being installed (so the app-password path has to stay as a fallback, i.e. two auth paths, not one), the SSO library speaks its own request/response types rather than Retrofit's, so `TickbuddyApi` would need a second implementation behind the interface, and JitPack hosting is a wrinkle for the F-Droid recipe. Roadmap item for further consideration, not scheduled.
- **`security-crypto` is alpha.** AndroidX is replacing it. Monitor and migrate when a stable replacement lands; for now the alpha is the only practical option for `EncryptedSharedPreferences`.
- **Tablet / large-screen pass.** `WindowSizeClass`-driven layouts, two-pane settings, expanded journal density. Out of scope while the product targets phone-only use; revisit if tablet/foldable usage becomes a goal.
- **Compose UI tests for the full `JournalScreen`.** Phase 5 covers `TickCell` interactions in isolation, but not the screen-level concerns (pull-to-refresh, sticky header scroll, infinite scroll, sync-issue chip rendering, overflow menu). Full-screen tests would need a Hilt test harness (`HiltTestActivity` + `@HiltAndroidTest`) and a fake `JournalViewModel`; the boilerplate per assertion is high. **Two regressions have now bitten** — both navigation, both shipped-and-caught-by-hand: the auth-state-driven `startDestination` that destroyed `JournalViewModel` mid-pull, and the `popUpTo(startDestinationId)` that resurfaced a signed-out user's credentials. Neither was detectable below the `NavHost` level, so this has graduated from "opportunistic" to the highest-value missing coverage: a harness that can drive sign-in → sign-out → sign-in and assert on the back stack and on `AuthUiState` being empty.
- **Toast assertions for locked cells.** `TickCellInteractionTest` only verifies that the boolean/counter callbacks don't fire when `editable=false`; it doesn't assert the Toast text. Asserting on `android.widget.Toast` from instrumentation is brittle. If we ever extract a `Toaster` seam (originally planned for Phase 5 but skipped) the assertion becomes trivial.
- **TalkBack `contentDescription` on tick cells.** Custom-drawn cells have no semantics, so a screen reader announces decorative children ("3", "checkmark") with no track / date / state context. Original plan called for `"Meditate, Sat April 25, ticked"`. Documented as a limitation for the initial release; revisit for an accessibility pass.
- **Inert columns in the schema.** `TickEntity.updatedAtLocal` and `TrackEntity.dirty/deleted` are unused (track management is online only and never sets them, so `reconcileTracks`' "unless dirty" branches never apply). Dropping one needs a full table rebuild (minSdk 31 ships SQLite 3.32, which has no `DROP COLUMN`; `tracks` is also the parent of the `ticks` foreign key), so by Martin's decision of 17 Oct 2026 they go in **their own** migration and change — which is why v4 (`MIGRATION_3_4`) adds to `ticks` but leaves `updatedAtLocal` alone. Until then, any future `PushWorker` change must guard against pushing tracks (the `dirty/deleted` columns shouldn't be interpreted as intent to push).
- **Toolchain upgrade (Kotlin / KSP / Hilt / AGP / Gradle) — completed 2026-07.** The coordinated AGP 9 wall was climbed in one jump. Final versions: **AGP 9.2.1, Gradle 9.4.1, Kotlin 2.3.20, KSP 2.3.9 (KSP2), Hilt 2.60, Room 2.8.4, kotlinx-serialization 1.11.0, androidx.core 1.19.0, androidx.lifecycle 2.11.0, androidx.hilt 1.4.0, compileSdk 37** (targetSdk stayed 36 — no runtime-behavior opt-in), JDK 17 (unchanged; AGP 9.2 needs 17). CI green (unit tests + lint + debug build). How it fit together, for whoever does the next jump:
  - **The two "walls" were actually one.** AGP 9 refuses to run the KSP1 backend (`KSP1 … no longer compatible with Android Gradle Plugin 9.0.0`), so AGP 9 *forces* KSP2 — and KSP2 was the thing that crashed this project. There was no AGP-9-on-KSP1 intermediate.
  - **The linchpin was Room, not KSP.** The KSP2 `unexpected jvm signature V` crash (google/ksp#2177) is triggered by Room 2.6's generated code for `suspend` DAO methods returning `Unit`; it was fixed in **Room 2.7.0-alpha11+**. Bumping Room to 2.8.4 is what made KSP2 viable. Room 2.8 also needs serialization ≥ 1.9 for its schema `$$serializer` (we're on 1.11.0), and serialization 1.11 needs Kotlin 2.3 — so the whole chain is `AGP 9 → KSP2 → Room 2.7+ → serialization 1.11 → Kotlin 2.3`.
  - **AGP 9 built-in Kotlin.** AGP 9 applies the Kotlin plugin itself, so `org.jetbrains.kotlin.android` was **removed** (from the version catalog `[plugins]` and both build files). We *adopted* built-in Kotlin rather than opting out (`android.builtInKotlin=false` + `android.newDsl=false` would have kept the old plugin, but that path dies in AGP 10). `kotlin.plugin.compose`, `kotlin.plugin.serialization`, and `ksp` stay in the `plugins {}` block; the Kotlin version is now resolved from those plugin versions (KGP floor is 2.2.10 with built-in Kotlin). The `kotlin { compilerOptions { jvmTarget = JVM_11 } }` block is unchanged and still valid. `ksp.useKSP2=false` was removed from `gradle.properties` (KSP 2.3.x is KSP2-only).
  - **Dagger 2.60 needs `error_prone_annotations` on the compile classpath.** Its generated code references `@CanIgnoreReturnValue`, but Dagger no longer brings the annotation transitively — added `compileOnly(libs.errorprone.annotations)` (CLASS retention, stays out of the APK). Distinct from the pre-existing `-dontwarn com.google.errorprone.annotations.**` R8 rule, which is a *runtime/shrink* concern.
  - **Room schema unchanged.** The 2.6 → 2.8 bump re-exported `app/schemas/` byte-identically (still v2) — no migration needed.
  - **`renovate.json` after the jump:** the five version caps (AGP, gradle-wrapper, core, lifecycle, room) are gone. Kotlin/KSP/Hilt are still grouped behind dashboard approval as **"Kotlin / KSP / Hilt (coordinated)"** — the wall is crossed, but the axis stays coupled (KSP locked to Kotlin, AGP built-in Kotlin resolves KGP from plugin versions, Hilt metadata parser, plus the Room↔serialization and Dagger↔errorprone couplings above), so the *next* Kotlin bump should still be done deliberately as one PR.
