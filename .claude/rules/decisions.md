# Scope decisions (v1)

The one-line form of each is in `CLAUDE.md`.

- **Auth**: pasted Nextcloud app password. Login Flow v2 stubbed but not implemented — seam exists in `AuthRepository.beginLoginFlowV2()`.
- **HTTPS only**: the early "Allow http://" toggle was removed. `ServerUrl.normalize` rejects anything but `https://`.
- **TLS trust**: `res/xml/network_security_config.xml` trusts `system` **and** `user` CA stores, so self-hosted servers behind a private/self-signed CA work once the user installs that CA on the device (issue #37). Chain, hostname and expiry are still fully verified — there is deliberately no "ignore TLS errors" switch, and adding one would be a regression (it is what Google's [policy page](https://support.google.com/faqs/answer/6346016) warns against, and the likely route to an F-Droid anti-feature). Two traps: the config **cannot** be narrowed with `<domain-config>` because the server hostname is entered at runtime and the file is a static resource; and `app/src/debug/res/xml/` **overrides** it in debug builds, so the debug copy must stay a superset of the main one or the feature silently vanishes from every build a developer tests on. Per-certificate trust-on-first-use (the model the Nextcloud Android client uses) is the stronger design and remains unbuilt — see `docs/backlog.md`.
- **TLS failures are classified, not lumped in with "unreachable"**: `SSLHandshakeException` / `SSLPeerUnverifiedException` are `IOException` subtypes, so without care they land in the generic "could not reach the server, check the URL and your network" branch — advice that points at three things that are all fine. `AuthProber` catches `SSLException` **before** `IOException` at all three probe stages (Kotlin matches catch clauses in order — the ordering is the whole mechanism) and returns `AuthProbeResult.UntrustedCertificate`; `SyncManager.pull` and `PushWorker` do the same for `SyncErrorKind.UntrustedCertificate`. Catch `SSLException`, **not** `CertificateException` — the latter is never the thrown type, only a cause several links down. And classify on exception *type*, never on `message` text: the wording comes from the platform TLS provider (Conscrypt on device, SunJSSE under JVM unit tests) and differs between them, so unmatched detail is passed through verbatim rather than guessed at. Coverage: `AuthProberTlsTest` (real TLS socket, cert from a CA the client doesn't know).
- **History depth**: full database, infinite scroll backwards in 30-day windows from day 1.
- **Private tracks**: simple show/hide toggle (App settings → Show private tracks). No PIN/biometric gate.
- **Counter UX**: short tap +1, long tap −1 (no-op when value is already 0).
- **Counter conflicts**: on a Tickbuddy with `counterIncrement` + `idempotencyKey` (2.3.0), a counter day goes up as the change made on this phone (`increment`), so other devices' and scripts' changes are kept (see "Push" in `.claude/rules/sync.md`). On an older server it is still silent last-write-wins: an absolute `set`, so two devices both incrementing on the same day lose one increment. Not surfaced in UI.
- **Sign-out**: calls `database.clearAllTables()`, resets `UiPreferences` (`clear()`) and clears `WidgetConfigStore` so the next user on the same device doesn't inherit cached data, queued writes, UI settings (theme, density, journal layout, editable-days, show-private), or widget setups. **Never `close()` the database here.** `TickdroidDatabase` is a Hilt `@Singleton`; nothing recreates it, so closing leaves every consumer (SyncManager, the repositories, the injected DAOs) holding a dead instance for the rest of the process, and signing back in without killing the app crashes on the first query with `SQLException: connection is closed`. An earlier version closed and deleted the DB *file* to avoid `clearAllTables()` running migrations on a stale on-disk schema; that trade was wrong — there is no destructive-migration fallback, so a stale schema crashes at startup long before anyone reaches sign-out. The wipe is gated on a real `SignedIn → SignedOut` transition (`SyncCoordinator` tracks the previous state) and runs under `SyncManager.runExclusive` so it can't race an in-flight pull. Regression coverage: `SyncCoordinatorTest.signOut_thenSignInAgain_leavesDatabaseUsable`.
- **Editability**: configurable in App settings. Choices: today only / today + previous day / last 7 days / all past days. Future days never editable. Tapping a locked cell shows a Toast.
- **Track management is online only**: add, rename, make private/public, reorder and delete are direct server calls made under the sync lock and followed by a re-read of the track list in the same hold (`SyncManager.changeTracks`, see `.claude/rules/sync.md`). There is no offline queue; offline, those controls are greyed out and a tap explains why. Colour and icon stay local (`track_prefs`) and editable offline. Changing a track's type is not offered (the server ignores it).
- **Archive / restore** (roadmap step 5b, needs a Tickbuddy with the `archivedTracks` capability flag; without it the app behaves exactly like 1.2.0 apart from the help sheet's offline sentence). Archive from the track screen ("Archive track" + confirm) or the delete confirm ("Archive instead", no second confirm); restore or delete from the collapsed "Archived (n)" row at the bottom of Tracks settings. Online only, like every track change. Archived tracks stay in Room (with their ticks, colour and icon) but never reach the journal, the widgets or widget setup. The archive date is the phone's own `clock.today()`.
- **Unknown track types are read-only, never a crash** (groundwork for Number / Choice, brief of 21 Oct 2026). `TrackType` is a sealed interface — `YesNo`, `Counter`, `Number`, `Choice`, `Unknown(wireValue)` — and `fromWire` never throws (it used to, from `TrackEntity.toDomain()`, which would have crashed every screen and widget redraw). Such a track shows everywhere — journal, Tracks settings, track screen, all three widgets and widget setup — with "Tickdroid update required" in place of its type label; its cells draw the ticked colour with "?" when the value is above 0 and the plain empty cell otherwise (no "·" / "+" hint); a tap (editable or locked day, journal or widget) only toasts "*Name*: Tickdroid update required." and its content description is "*Name*, Tickdroid update required". Track management (rename, Private, colour, icon, reorder, archive, restore, delete) is untouched. Widget taps use `ReadOnlyTapAction` (carries `KeyTrackName`, writes nothing, so no stale-day check); `WidgetTickHandler.onTap` also returns `Ignored` for one as a guard. The shared strings are in `ui/common/UpdateRequired.kt`. `NewTrackSheet` saves the type's wire value in `rememberSaveable` (a sealed type isn't Bundle-able). **For the release that first learns a new type** (agreed 21 Oct): it must delete the local ticks of every track whose type it newly understands on first start (they hold the older release's 1/0 markers, see "Network" in `.claude/rules/data.md`), and keep such a track locked until its first successful sync after the update, or an offline install could overwrite the server's value. 1.6.0 did this for `number` and `choice` (`MIGRATION_5_6` + `awaitingSync`, see "Number and Choice"); a later type repeats it.
- **Number and Choice** (Tickbuddy 3.2.0, spec "Number and Choice track types", decisions of 17–18 Nov 2026). A **Number** day is a reading, stored as **whole thousandths in `ticks.value`** (10.4 is 10400, −1.5 is −1500), exactly as the server stores it (`Int` holds its whole ±2,147,483.647 range); a **Choice** day stores the option's **place** (1 to n). **For both, "has an entry" is "has a row", never `value > 0`**: 0 and negative Numbers are entries (`TickCell`, `WidgetRow.done`, the squares' level and dashed outline, the descriptions). All decimal maths is in `domain/NumberValue.kt` (pure, `BigDecimal` + `java.text`, `NumberValueTest`): `numberFromWire` (from the JSON number's own text, never a `Double`; refuses an exponent or > 3 decimals), `numberToWire` (point, no grouping, no trailing zeros), `roundMilli` (half away from zero), `formatNumber` (locale separators, no "−0.0"), `parseTyped` (one `.` or `,` as the decimal separator, `-` or `−`; `Empty` / `Value` / `NotANumber` / `Negative` / `TooLarge`), `ungroupPasted` (the web's grouping rule, pastes only) and `shortLabel` (a Choice label's emoji or two graphemes in capitals; the emoji test is a parameter, ICU's `Extended_Pictographic` on the phone). Writes are absolute: `TickRepository.setValue` (null clears: marks the row deleted, never deletes) → `PushWorker.pushValue` (`POST /ticks/set value=…`, `""` to clear, no read, no key) → `settleValue`, which **never deletes at 0** (unlike `settleTo`). Settings (unit, decimal places, allow negative; options, ordered scale) are server state, changed online through `TrackEditor` as Private is; "Journal cells" (`TrackPrefs.cellLabel`: short label or place number) is phone-only like colour. **First start after 1.5.0:** `MIGRATION_5_6` deletes every `number`/`choice` track's ticks (1.5.0's markers) and sets `tracks.awaitingSync`; only a **successful pull** clears it (`TrackDao.clearAwaitingSync`, in the pull's transaction — never `changeTracks`' re-read, which reads no ticks). While set the track's cells are empty with no hint, a tap toasts "*Name* can be changed after the next sync." (T20), the widget window closes with it, the push drops any dirty row unsent, and the track screen hides the type settings. `Track.isEditableType` / `Track.entersValue` are the helpers. New track offers Number only with the `numberTracks` flag and Choice only with `choiceTracks`.
- **Today and the bottom bar** (spec "the Today screen and notes", decisions of 28 Oct 2026). Two main screens, **Today** and **Journal**, each with a Material 3 `NavigationBar` (web icons: `CheckBox`, `CalendarMonth`, filled when selected). Today opens **only on a start from nothing** (swiped from recents, reboot, update, any sign-in); coming back to the app, by recents, launcher or widget, always returns to the screen that was left (the platform's own saved state; nothing is stored for it). Tapping Today in the bar shows today; Back on the Journal goes to Today, Back on Today leaves the app, except right after a Journal day label opened it (then Back returns to the Journal, until a bar item is tapped).
- **Notes** (Tickbuddy flags `notes` / `notesAppend`): one plain-text note per track per day, at most 500 code points, read and written on Today in a card docked over the keyboard, marked with a dot in the Journal. Written to Room straight away and pushed later; a note changed elsewhere meanwhile is **merged with `append`** (only the phone's new lines go up, nothing on the server is removed), or overwritten by the phone's version on a server without `notesAppend`. Without `notes` there is no note UI anywhere and no notes request. Notes on a track of an unknown type can be read and written (only its cell is read-only).
- **Streaks come from the server** (`GET /api/stats?today=…`, flag `stats`), read at every pull and kept in Room (`track_runs`), so they show offline but only update after a sync (a second or two after a tick online). No phone-side streak rule. Without `stats`, no streak text.
- **Out of scope for v1** (deferred): Login Flow v2, import/export, daily reminder, real schema migrations.
